💻 Synthèse — Programmer l'alerte

Comment modifier le programme de la station sans rien casser — et le prouver par des tests ?

1. La carte d'identité du programme (3e_C6.1)

Données utilisées = lues de l'extérieur (capteurs, constantes) · données produites = créées par le programme (résultat, commande, message). Tracer = exécuter à la main pour prédire les sorties. Les elif s'arrêtent au premier test vrai → on teste les seuils du plus FORT au plus FAIBLE. L'opérateur > est strict : à la frontière exacte, le test échoue.

2. Modifier (3e_C6.3)

Paramètre
changer la constante nommée (SEUIL_ORANGE = 60) : un seul point de modification.
Nouvelle fonctionnalité
suivre la spécification (algorigramme) en imitant les modèles existants : initialisation sûre (False) → décision (branches) → commande (if final).
Indentation
en Python elle EST la structure : 4 espaces = « dans la branche ».

3. Valider (3e_C6.3)

Jeu d'essai
entrée + sortie attendue calculée à la main AVANT + sortie obtenue + verdict ✔/✘.
Frontières
tester seuil−1, seuil, seuil+1 : seuls points où > et >= diffèrent.
Non-régression
re-tester AUSSI l'ancien comportement.
Verdict
UN échec = version refusée → corriger → tout rejouer.

🛠 Je dois savoir faire

  • établir la carte d'identité entrées/sorties d'un programme ;
  • tracer une exécution à la main ;
  • modifier un paramètre et prédire l'effet ;
  • ajouter une fonctionnalité en imitant un modèle existant ;
  • construire et dérouler un plan de tests aux frontières.

⚠ Erreurs à éviter

  • Lire > comme >= (LE piège des frontières : 118 > 118 est FAUX) ;
  • tester les seuils dans l'ordre croissant avec des elif (l'ouragan serait classé orange !) ;
  • oublier l'initialisation à False ou l'indentation des branches ;
  • « tester » sans avoir calculé la sortie attendue à la main ;
  • ne tester que la nouveauté et oublier la non-régression ;
  • accepter une version avec un test en échec (4/5 = refusé !).
